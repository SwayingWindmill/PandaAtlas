# Mobile app and platform services

How the Expo app (`apps/mobile`) uses Supabase and Cloudflare within the [architecture baseline](zhipanda-v2-architecture-baseline.md). It applies the baseline to one more client and settles nothing new: the app is a client of the V2 API like the website ([ADR-0001](adr-0001-single-source-api-boundary.md)).

| Service                 | In the app           | Why                                                                                                                                                                                                                                                                                                                              |
| ----------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Supabase Auth           | Used                 | Email-code sign-in (`signInWithOtp` / `verifyOtp`), the session in Expo SecureStore (chunked under Android's 2 KB limit), auto-refresh on foreground, and TOTP (`auth.mfa`) as the step-up the `privacy.request.manage` policy requires (AAL2 and recent authentication). The access token is the bearer token for `/me` routes. |
| Supabase Postgres       | Used through the API | Every read and write goes through the NestJS API (§13 public reads, §11 events). The app never queries tables directly.                                                                                                                                                                                                          |
| Row-level security      | Not exposed          | The Data API is off (#671), so no client reaches tables. Ownership and capabilities are enforced in the API's access guard (§10), and the app-role grants test keeps the database role to what the API uses.                                                                                                                     |
| Supabase Storage        | Not used             | Media lives in R2 (§14). Contribution attachments, if fans may upload them, go to R2 through presigned URLs the API authorizes (§14), not Storage.                                                                                                                                                                               |
| Supabase Realtime       | Not used             | It would need tables exposed through the Data API, which ADR-0001 rules out. The inbox and 今天 refresh when their screen comes into focus, which matches how often their content changes (per release, at most every Cron cycle).                                                                                               |
| Supabase Edge Functions | Not used             | Business logic lives in the API Worker (ADR-0002). A second server runtime for the same rules would duplicate them.                                                                                                                                                                                                              |
| Cloudflare Workers      | Used                 | The API Worker serves every app request, and its Cron Trigger runs the downstream cycle (notifications, privacy requests, updates) (§19).                                                                                                                                                                                        |
| Workers Cache           | Used                 | Public reads and `/media/*` photos are cached at the edge (§13, §14). On the device, successful public reads are also saved (AsyncStorage, network first), so an app started offline shows them.                                                                                                                                 |
| Cloudflare R2           | Used                 | Panda photos the app shows, the photo viewer and share cards come from R2 through `/media/*` (§14).                                                                                                                                                                                                                              |
| Cloudflare Queues       | Not used             | Asynchronous work already runs on the Postgres outbox and PGMQ, dispatched by the Cron Trigger with at-least-once delivery (§11). A second queue would split that delivery path.                                                                                                                                                 |
| Workers KV              | Not used             | No app data is a key-value read that Workers Cache or the release-scoped tables do not already serve.                                                                                                                                                                                                                            |
| Hyperdrive              | Used indirectly      | It connects the API Worker to Postgres, so app requests reach the database through pooled connections (§19).                                                                                                                                                                                                                     |

## Verification

The app's journeys run against the real stack: Playwright drives the Expo web build against the local API and local Supabase (Auth codes from the local mail catcher, TOTP from the secret the app shows, the Cron cycle run in-process). The fixture data comes from the API's own domain modules and a published release. See `apps/mobile/README.md`.
